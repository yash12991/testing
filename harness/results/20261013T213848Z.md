`detection (s)` is the true wall-clock gap between this harness's `kubectl apply` and the Observer's `anomaly_detected` row (see `report.py`'s module docstring for why `aggregate_results` itself cannot compute this and `main()` overwrites it below). `detection→recovery (s)` is `aggregate_results`'s `mttr_s` field: `anomaly_detected -> verification`, recorded for every incident that reached verification regardless of outcome. Despite what its field name suggests, THIS IS NOT THE SPEC'S MTTR METRIC — it is detection-to-recovery, dominated in practice by the Verifier's fixed ~30s backoff regardless of scenario, so it badly understates true repair time. `MTTR (s) [injection→recovery]` is the actual spec metric: the wall-clock gap between this harness's `kubectl apply` (`injection_ts`) and the incident's real `verification` row in Postgres, computed the same way `detection (s)` is (see `compute_true_mttr_times`). `diagnosis_correct`/`remediation_success` are counted against `detected`, not `attempted`.

## Interpreting these results

- **pod_crash's "remediation success" may partly reflect Kubernetes' own self-healing, not solely the orchestrator's fix.** `pod-crash.yaml` uses Chaos Mesh's `container-kill` action, which is one-shot: the kubelet restarts the killed container in place within seconds, independent of whether the Fixer's `restart_pod` action (which deletes the pod so Kubernetes reschedules it) ever ran. Verification happens within the ~60s window after `fix_executed`, by which point the kubelet may have already restarted the container on its own. So a `recovered: True` / `remediation_success` count for pod_crash does not cleanly isolate "the orchestrator fixed it" from "Kubernetes would have fixed it anyway regardless of what the orchestrator did." This is a known, documented limitation of the current chaos-injection timing for this scenario, not something this report's numbers correct for — read pod_crash's remediation_success with that caveat in mind.
- **cpu_stress's `cpu_ratio` now uses `max(...)` across matching pods, not `avg(...)` (final-review Fix 3).** Averaging previously meant that once `scale_replicas` added idle replicas, the cluster-wide average diluted below threshold even though Chaos Mesh's `mode: one` selector kept stressing only the original pod — so `recovered: True` used to mean "the average got diluted," not "the stressed pod itself recovered." With `max(...)`, verification now reflects the worst/most-stressed matching pod, which is a more honest (and typically slower-to-satisfy, or possibly never-satisfied within the resolution timeout) signal of real recovery.
